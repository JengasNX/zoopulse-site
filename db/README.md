# Серверный фундамент

## Фактическое состояние

Две миграции проверены на PGlite (PostgreSQL в WebAssembly, временная БД
в памяти). Это проверка настоящего SQL, ограничений и транзакций, но
**не проверка сетевого PostgreSQL, RLS, авторизации или рабочего backend**.
Публичный каталог по-прежнему использует демонстрационные данные.

- `001_core.sql`: организации, членство, модерация, питомцы, заявки, согласия,
  изображения, аудит и очередь уведомлений.
- `002_integrity.sql`: запрет фото чужой организации, согласий чужого заявителя,
  пустых имён и автоматический `updated_at`.
- `migrate.mjs`: последовательное применение, SHA-256, журнал, отказ при
  несовпадении истории; DDL и запись журнала в одной транзакции.
- `scripts/db-migrate.mjs`: подключение через `pg`, advisory lock на выделенном
  соединении, обязательное подтверждение целевой БД. Ошибки без SQL/контактов/URL.
- `src/server/database.ts`: ленивый server-only pool и транзакции.
- `src/lib/access-policy.ts`: проверяемые предикаты, пока **не серверная граница
  доступа**. Нет HTTP endpoints, сессий или применения RLS.

Ранний `001_core.sql` был только черновиком, не применявшимся к сервисной БД.
Внешние BEGIN/COMMIT удалены: транзакциями теперь управляет runner.
Если вы применяли черновик вручную, не запускайте поверх него эту миграцию:
нужно отдельное сопоставление схемы/истории, не удаление данных.

## Проверки без Docker

Node.js 22.18+:

```powershell
npm ci
npm test
```

Тестовая БД создаётся в памяти и закрывается по окончании теста. Демо-каталог
в неё не переносится. Тесты проверяют SQL, откат неудачной миграции,
контрольные суммы, изоляцию связей организаций, повторные ключи заявок,
права гостей/владельцев/модераторов, запрет чтения чужих заявок.
Не проверяются SMTP, сетевые блокировки и конкурентные запросы.

## Локальный PostgreSQL — подготовлен, ещё не запущен

Нужен работающий Docker Desktop. `compose.yaml` предназначен только для
локальной разработки: порты привязаны к 127.0.0.1, dev использует свой
volume, test — отдельный временный tmpfs.

```powershell
# Придумайте отдельный локальный пароль. Не используйте production-секреты.
$env:ZOOPULSE_DEV_DB_PASSWORD = '<local-password>'
docker compose up -d db-dev

# При спецсимволах URL-кодируйте пароль.
$env:MIGRATION_DATABASE_URL = 'postgresql://zoopulse_migrator:<url-encoded-password>@127.0.0.1:55432/zoopulse_dev'
$env:CONFIRM_DATABASE_MIGRATION = 'yes'
npm run db:migrate
```

Runner сам `.env` не читает; используйте переменные процесса.
Для test: `docker compose --profile test up -d db-test`.
**Не выполняйте `down -v` для очистки:** это удалит dev-данные.
Test tmpfs теряет данные при остановке контейнера.

## До реального backend

1. Выбрать поддерживаемую авторизацию, её таблицы и связь с `app_user`.
2. Сессия и членство загружаются только сервером. Нельзя принимать `Actor`,
   роли и membership из тела запроса как доверенные.
3. Реализовать DAL: минимальные DTO, параметризованные запросы, проверки
   прав и актуальных статусов в транзакции; тесты двух организаций.
4. Разделить владельца миграций и непривилегированную роль приложения.
   Runtime не получает `MIGRATION_DATABASE_URL`; приложение не запускает DDL.
5. Настроить grants/RLS, TLS с проверкой сертификатов, бэкапы/восстановление,
   лимиты и конкурентные тесты на обычном PostgreSQL.
6. Запись заявки, согласий, задания уведомления и аудита — атомарно;
   идемпотентность требует обработки конфликта, не только UNIQUE-ограничения.

Предикаты сейчас запрещают незаметное изменение одобренного профиля:
потребуется отдельная версия профиля и повторная модерация. Модератор
не одобряет собственную организацию; глобальная роль не даёт автоматический
доступ к контактам заявителей. Приостановленная организация не читает входящие.
Привилегированный обход возможен только в будущем отдельном аудируемом процессе.

Сроки хранения/удаление и документы нужно согласовать до реального сбора данных.
Не используйте Compose, тестовые пароли и тестовые данные в production.
