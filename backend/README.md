# Backend: локальная авторизация и организации

Это отдельный Node.js-процесс, **не API GitHub Pages**. Публичный Next.js-сайт
не подключён к нему и не собирает настоящие регистрационные данные.

## Реализовано

- Better Auth 1.7: email/password, обязательная проверка почты, сессии 24 часа,
  выход, восстановление пароля с отзывом сессий, ограничения частоты запросов.
- Cookie HttpOnly/SameSite=Lax; Secure для HTTPS; кэш сессии в Cookie отключён.
- Таблицы библиотеки отделены от `app_user` и бизнес-ролей (`003_auth.sql`).
- Доверенный `Actor` создаётся из проверенной сессии и БД. Клиентские
  `role`, `userId`, `status`, `createdBy` не принимаются.
- `GET /api/me`: минимальная текущая идентичность.
- `POST /api/organizations`: черновик, членство owner, запись аудита
  в одной транзакции.
- `GET /api/organizations/:id`: публичный профиль или собственный черновик.
  Чужой закрытый и несуществующий профиль одинаково отвечают 404.
- Ограничение тела 20 KiB, Origin-проверка изменяющих запросов, no-store,
  нормализация ошибок без URL/SQL/паролей/контактов.
- Авторизация выключена по умолчанию. Нет обходного «демо-входа»,
  предустановленного администратора, статичных паролей или логирования токенов.

## Проверки и границы

```powershell
npm ci
npm test
npm run build
```

Auth-тесты вызывают настоящий Better Auth handler: подтверждение почты,
вход/выход, подделанная Cookie, сброс пароля, отзыв сессий, Origin, rate limit.
**Используется memory adapter только в тестах**, письма перехватываются в памяти.
HTTP/DAL-тесты используют PGlite и подменённый валидатор сессии, чтобы
независимо проверить права, скрытие данных, валидацию, атомарный откат.
SQL-миграция также сверяется с набором колонок установленной версии Better Auth.

Это **не полный E2E на PostgreSQL+SMTP**. Не проверены реальные почтовые
провайдеры, доставка/повторы, конкурентность, RLS и несколько инстансов.
Форм входа/регистрации/сброса пароля в интерфейсе ещё нет.

## Безопасный запуск без аккаунтов

```powershell
npm run backend
```

Привязка только к 127.0.0.1:3004. `GET /health` доступен,
`/api/*` отвечает 503. Секреты/БД/SMTP для такого запуска не нужны.

## Включение локального сценария

Сначала миграции из `db/README.md`. Нельзя запускать миграции от runtime-роли.
Затем задать переменные **только серверного процесса**:

| Переменная | Назначение |
|---|---|
| `DATABASE_URL` | отдельная runtime-роль PostgreSQL |
| `BETTER_AUTH_SECRET` | случайный секрет минимум 32 символа |
| `BETTER_AUTH_URL` | origin сервиса, локально `http://localhost:3004` |
| `SMTP_HOST`, `SMTP_USER`, `SMTP_PASSWORD` | SMTP с TLS на порту 465 |
| `MAIL_FROM` | разрешённый почтовым сервисом отправитель |
| `AUTH_ENABLED=true` | явно включает auth и бизнес-API |
| `AUTH_REGISTRATION_ENABLED=true` | отдельно разрешает создание аккаунтов |
| `BACKEND_PORT` | необязательно, по умолчанию 3004 |

Секрет можно сгенерировать: `node -e "console.log(require('node:crypto').randomBytes(48).toString('base64'))"`.
Не отправляйте результат в GitHub, чат или публичные логи.

`npm run backend` не читает `.env`. При использовании локального файла:
`node --env-file=.env.backend --import tsx backend/index.ts`.
Файлы `.env*` исключены из Git.

Включённый сервер проверяет доступность таблицы auth_user и SMTP при старте,
не создаёт таблицы автоматически. При ошибке не начинает слушать порт.
Email отправляется вне HTTP-ответа, ошибки не раскрывают существование адреса.
Задания доставки сейчас только в памяти процесса: при падении сервера письмо
может потеряться; требуется повторная отправка. Постоянную очередь нужно
добавить перед пилотом.

## Развёртывание — пока не готово

Первый вариант — frontend и `/api` под одним HTTPS-origin через reverse proxy.
CORS, cross-site Cookie и доверие произвольному `X-Forwarded-For` не включены.
IP для лимитов берётся из сокета, входной заголовок перезаписывается.
За proxy все пользователи пока разделят лимит его IP: настройку доверенных
proxy и защиту внешнего входа нужно сделать до публикации.

До реальных пользователей: runtime grants/RLS, обычный PostgreSQL E2E,
проверка резервных копий, постоянная доставка писем, rate limits бизнес-API,
формы и версии согласий, ограничения регистрации, реквизиты/документы,
сроки хранения сессий/IP/данных и юридическая проверка.
Email-подтверждение не является согласием на обработку персональных данных.
Публичную регистрацию до выполнения этих условий не включать.
